# Footie multi-agent benchmark

The application remains hosted in Azure Container Apps. This benchmark evaluates
Footie's bounded Match Analyst/Career Analyst delegation, independently of whether
Foundry monitoring is configured. A tracing connection is not evidence of answer
quality.

## Protocol

The [34-case regression corpus](../../fixtures/assistant/multiagent_questions.json)
adapts the evaluation structure of [Brian Benz's football benchmark](https://github.com/bbenz/football-results-dashboard/blob/main/demo/src/football_insights/evaluation/cases.yaml):
tool selection, numerical grounding, unsupported requests and responsible framing.
It uses Footie's synthetic club/player records, not the national-team questions
whose source data Footie does not contain. The existing single-agent question
corpus and earlier reports remain unchanged.

The cases cover player metrics, goalkeeper ratios, unavailable measures,
comparisons, form, season and metric follow-ups, club records, moral framing,
unsupported requests, playback cutoffs, unavailable/stale moments, retractions,
and four combined match/history questions. Expected query plans and specialist
roles are authored labels, not outputs generated by the router under test.

An additional [eight paraphrases](../../fixtures/assistant/multiagent_heldout.json)
were authored separately and excluded from runtime prompts. They are a small
diagnostic set, not a statistical accuracy estimate. Once a failure informs a
fix, subsequent results on that question are regression results, not unseen
validation.

The oracle calculates expected answers from the authored plans through existing
canonical reducers. It checks interpretation, evidence consistency, and the
application's numerical outputs; it is **not an independent arithmetic audit** of
the reducers. Existing accounting and positional-distribution tests remain
necessary.

For replay/history questions, the expected match portion uses the selected
playback cutoff, while the career portion includes only completed matches before
kickoff. The milestone fixture provides a concrete anchor: 73 prior career goals,
then two goals in the featured match produce the recorded 75-goal milestone.
End-of-match aggregates must not leak into the pre-match comparison.

Scoring distinguishes:

- Exact authored intent: operation, subjects, metrics, season and rate scope.
- Exact facts, evidence references, availability/null values and navigation actions.
- Exact single-domain charts; compound chart items must come from approved facts
  or canonical component charts.
- Narrative statements, their linked facts, and coverage of both requested
  specialist perspectives.
- Successful delegation/completion versus safe fallback or partial failure.
- Provider-call limits, reported tokens, missing usage reports and elapsed time.

A partial specialist result or a correct calculated fallback can remain useful
to the user, but cannot count as complete multi-agent success. A mock-provider
pass proves runtime contracts, not that a model understood the question.

## Budget and privacy

Evaluation uses the existing persistent ledger at ignored
`var/footie-evaluation-budget.sqlite3`. No ledger is deleted or replaced. The
multi-agent runner now permits at most 240 provider attempts per rolling hour and
400 per rolling day, with an additional explicit per-run cap (default 20).
Legacy evaluation commands retain their 20-per-hour default. All commands share
the same recorded attempts; a failed request consumes its reservation.

The first frozen runs used a 120-per-hour ceiling. After their failures were
recorded, the review explicitly authorized a 240-per-hour evaluation-only ceiling
for bounded follow-up checks; the ledger and existing charges remain intact.

The regression corpus has a conservative upper bound of 66 provider attempts;
each eight-question additional set has an upper bound of 18. These are request bounds,
not dollar estimates or a statement of remaining Azure credit. This allowance
does not replace the public application's separate admission controls.

Reports contain authored case IDs, typed plans, aggregate usage, operational
failure reasons and source hashes. They omit credentials, model endpoints and
raw user conversation bodies. Live evaluation calls the existing model through
an isolated local FastAPI application; it does not mutate production records.
Correction cases use disposable local overlays.

The runner hashes source files before execution and checks them again afterward.
Source changes or exhausted allowance mark a run incomplete. Reports refuse to
overwrite existing paths.

## Commands

Offline lookup baseline (no agent and no model calls):

```sh
.venv/bin/python scripts/evaluate_footie_multiagent.py --output var/footie-multiagent-baseline-new.json
```

Real framework with authored provider replies (no model calls):

```sh
.venv/bin/python scripts/evaluate_footie_multiagent.py --mock --output var/footie-multiagent-mock-new.json
.venv/bin/python scripts/evaluate_footie_multiagent.py --mock --heldout --output var/footie-multiagent-heldout-mock-new.json
```

Full live regression and separate paraphrase run, with bounded opt-in:

```sh
.venv/bin/python scripts/evaluate_footie_multiagent.py --azure --all --max-attempts 66 --output var/footie-multiagent-azure-new.json
.venv/bin/python scripts/evaluate_footie_multiagent.py --azure --heldout --max-attempts 18 --output var/footie-multiagent-heldout-azure-new.json
```

Without `--all`, live regression selects eight cases authored before results
were observed. `--case <id>` selects a targeted check; it is not a full-suite
result. Exit codes are 0 for pass, 1 for failed checks, and 2 for incomplete
execution. The lookup baseline will fail agent-completion checks by design;
compare its factual coverage rather than its overall completion score.

Independent evaluator/legacy regression tests:

```sh
.venv/bin/pytest -q tests/test_multiagent_benchmark.py tests/test_assistant_evaluation.py
```

```text
114 passed in 52.05s
```

The tests deliberately corrupt subject, scope, value, evidence, chart, action,
narrative, route and completion state; they also exercise daily/hourly allowance
continuity and the pre-match boundary. Runtime integration tests additionally
cover provider failure, cached bundles and revisions arriving during synthesis.

## Initial results — preserved before fixes

| Run | Answer/intent checks | Complete benchmark pass | Provider attempts |
| --- | ---: | ---: | ---: |
| Offline lookup baseline | 29/34 | Not an agent run | 0 |
| Authored mock-provider regression | 34/34 | 34/34 runtime contracts | 0 paid; 59 mocked |
| Initial Azure regression | 29/34 | 22/34 | 61 |
| Initial Azure additional questions | 6/8 | 5/8 | 18 |

The first two live reports are retained as
[initial regression](footie-multiagent-azure-initial.json) and
[initial additional questions](footie-multiagent-heldout-azure-initial.json).
The [lookup baseline](footie-multiagent-lookup-baseline.json) retains all expected
agent-completion failures rather than presenting a lookup as AI execution.

`facts_passed` in these reports is a composite of intent, facts, actions, visual,
narrative and explicit anchors. It is not merely a count of correct numerical
values. `workflow_completed` counts whether the agent completed even if its
answer subsequently failed semantic checks. Neither alone is the release gate.

The initial regression and lookup baseline correctly marked themselves
**incomplete** because `observability.py` changed during execution. The change
concerned tracing operation labels, not football query logic. Their individual
case diagnostics remain useful, but these are not reproducible final release
certificates. The additional-question live run had no source changes and failed
its quality checks normally.

Concrete failures:

- A club-total question was answered with a player leaderboard. Both were valid
  database queries, but the operation was wrong and the validator accepted it.
- Vague superiority/comparison questions silently defaulted to goals rather than
  asking which measure the user intended.
- A goalkeeper-ratio paraphrase returned saves and shots, not save percentage.
  Even an authored correct save-percentage mock plan was rejected by the old
  metric guard, so this was not solely a model interpretation problem.
- Several final sentence selections failed validation and used calculated
  fallbacks. Those remain grounded answers but were not counted as successful
  model completion.
- One compound answer omitted the career perspective from its narrative despite
  returning both sets of facts. Another suffered a partial Match Analyst failure.

The initial regression's p50/p95 was 6,606/14,016 ms; the eight additional cases
measured 5,402/8,642 ms. These small single-run samples include local application
work and network time; they are not an Azure production SLA.

Together the initial live runs consumed **79 provider attempts**, reporting
**160,644 input tokens and 2,770 output tokens (163,414 total)**. One attempt had
unreported usage, so reported tokens are a lower bound on potentially billable
usage. No dollar-cost claim is inferred from these counts.

After recording those failures, eight new questions were independently authored
in [the fresh holdout](../../fixtures/assistant/multiagent_fresh_holdout.json),
before the runtime fixes. They were not sent to the implementation agent or put
in prompts. `--fresh-heldout` selects this set. The original additional questions
must be called regression checks after their failures inform changes.

### Targeted second pass

The [seven-case targeted v2 run](footie-multiagent-azure-targeted-v2.json) used
15 attempts and passed 4/7 complete-workflow checks, with unchanged source
hashes. No broad final run was started after this failed gate.

Typed selection diagnostics exposed two concrete schema weaknesses: a selection
repeated the same sentence ID as both lead and support, and another selected two
match sentences while omitting the requested career perspective. Both fell back
to validated calculated stories. A club-total planning response failed before
query validation; this run did not capture its raw typed proposal, so its exact
cause cannot be claimed from the report.

The next revision replaces independently selected sentence IDs with an enum of
prevalidated story bundles, and captures bounded query-proposal diagnostics.
The independent evaluator was also updated to distinguish correct calculated
fallback facts from failed model completion, and its canonical oracle questions
now explicitly encode the authored operation and rate to satisfy the stronger
production validation. Earlier reports remain unchanged.


## Frozen third revision — full regression and first fresh holdout

The bounded story-bundle change passed its gates: seven targeted regression
questions passed 7/7 using 16 attempts, and the earlier goalkeeper paraphrase
passed 1/1 using two attempts. These are regression checks informed by earlier
failures, not unseen model-quality evidence.

The next three runs used unchanged inference and evaluation source hashes:

Exact commands:

```sh

.venv/bin/python scripts/evaluate_footie_multiagent.py --azure --heldout --max-attempts 18 --output docs/verification/footie-multiagent-heldout-regression-final-v3.json

```

The full regression's one incomplete workflow returned a safe clarification
through calculated fallback after an SDK-stage failure. It reported no query
proposal or token usage, so the exact underlying cause cannot be established.
It remains a failed complete-workflow case, despite correct final clarification.

The first fresh holdout exposed three remaining interpretation defects:

- “Which Redhaven player has the highest total for key passes?” was answered with
  the club total instead of a player leaderboard.
- “What percentage of the shots on target Leon Finch has faced did he save?”
  returned shots and saves instead of save percentage.
- The career portion of a selected-goal question asking for two players' goals
  per 90 before the match was classified unsupported. The match answer remained
  grounded and the partial-result notice was present, but the requested comparison
  was missing.

These results **do not establish an all-pass release gate**: the combined final
sets passed 46/50 complete-workflow checks and 47/50 answer/intent checks. All 50
passed routing and call-bound checks. The fresh set is now regression material
because its failures inform subsequent fixes. No new holdout is substituted to
hide these outcomes.

The three frozen runs reported 203,521 input and 3,012 output tokens (206,533
total), with one unreported-usage attempt. Across every retained paid evaluation
through these runs, 206 attempts reported 442,485 input and 6,967 output tokens
(449,452 total), with two unreported-usage attempts. These totals exclude any
unrelated application traffic and are not dollar-cost estimates.

The runtime's stronger safeguards improve the authored regression over the
initial result, and all four cross-specialist regression cases now pass. This is
not a randomized single-agent/multi-agent comparison: the lookup baseline was
captured before guard fixes, and the oracle reuses canonical reducers. Remaining
paraphrase brittleness and a single-run network failure must be reported openly.


## Release-candidate regression after disclosed failures

The three disclosed failures were corrected through broader intent safeguards,
with positive and negative runtime tests: player superlatives versus club totals,
goalkeeper percentages versus two separate counts, and explicit pre-match career
comparisons versus current-match statistics. The typed pre-match scope removes
only the historical qualifier for planning and clears the unused match selection,
while retaining the original task span, kickoff cutoff and visible history label.

The same release-candidate sources passed:

| Check | Result | Paid attempts |
| --- | ---: | ---: |
| [Three disclosed failure regressions](footie-multiagent-disclosed-regression-v4.json) | 3/3 all checks | 8 |
| [Earlier SDK-failure case recheck](footie-multiagent-sdk-regression-v4.json) | 1/1 all checks | 1 |
| [Full authored mock regression](footie-multiagent-mock-final-v4.json) | 34/34 runtime contract checks | 0 |
| [Same-source lookup baseline](footie-multiagent-lookup-final-v4.json) | 29/34 answer/intent checks | 0 |

Exact commands:

```sh
.venv/bin/python scripts/evaluate_footie_multiagent.py --azure --fresh-heldout --case fresh_club_creation --case fresh_keeper_percentage --case fresh_moment_rates --max-attempts 8 --output docs/verification/footie-multiagent-disclosed-regression-v4.json
.venv/bin/python scripts/evaluate_footie_multiagent.py --azure --case multi_ambiguous_metric --max-attempts 2 --output docs/verification/footie-multiagent-sdk-regression-v4.json
.venv/bin/python scripts/evaluate_footie_multiagent.py --mock --output docs/verification/footie-multiagent-mock-final-v4.json
.venv/bin/python scripts/evaluate_footie_multiagent.py --output docs/verification/footie-multiagent-lookup-final-v4.json
```

All four reports found no source changes during execution. Although the CLI
selector remains `--fresh-heldout`, the three disclosed cases are now regression
checks. Their original first-unseen score remains **5/8**, not revised to 8/8.
The lookup baseline's five intent failures were the four compound questions and
an ambiguous-superiority question returning a safe unsupported response instead
of a clarification; its overall agent-completion failures are expected by design.

The earlier full live v3 run predates these intent changes and the Azure exporter
privacy correction. It must not be described as a full live run of identical v4
release sources. The v4 evidence combines focused live regression, full mock
contracts, independent evaluator tests, and the broader runtime/CI suite. A later
full live run, if performed within the existing rolling allowance, is additional
verification and should be reported with its own source hashes.

Cumulative retained paid evaluation through v4 used **215 attempts**, reporting
**463,688 input and 7,283 output tokens (470,971 total)**, with two attempts lacking
usage reports. All previous charges remain in the shared ledger. No additional
unseen set was repeatedly sampled to obtain a perfect score.
