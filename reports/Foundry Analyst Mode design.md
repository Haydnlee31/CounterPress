# Bring Footie’s Match Intelligence Into Foundry

**Build Analyst Mode as a separate full-match experience, backed by a Foundry-hosted coordinator and four native prompt-agent specialists.** Keep the existing Footie assistant intact. The strongest improvement is a shared, time-bounded view of the match that specialists interpret from different football perspectives, followed by a director that publishes only useful, supported findings. The supplied video and repository describe two different projects; neither inspected implementation reads real match footage. Their useful patterns are synthetic telemetry, deterministic statistics, event prioritization and concise explanations. Native Foundry orchestration would go beyond both references. This document is an implementation decision brief, checked on **26 October 2026**; it does not claim the new feature has been built or deployed.

## Two references offer useful patterns, with limits

The YouTube link is **Matchday Crew**, whose description links to `timsheldon1/matchday-crew`. Its three Foundry prompt agents are Explainer, Storyteller and Recapper; Node application code runs their queue and handoffs. MatchMind has six pipeline roles—Vision, Interpreter, Explainer, Narrator, Personalizer and Renderer—but only three use language models. Python application code orchestrates them. **Registering agents in Foundry and tracing their calls is distinct from running the orchestration in Foundry.** ([Video](https://www.youtube.com/watch?v=HxED-0T8Unw), [Crew native agent calls](https://github.com/timsheldon1/matchday-crew/blob/374de95f4f7474c9a784e01a3ceafb2ce0a16ad5/src/agents/foundry.js), [MatchMind orchestration](https://github.com/auroraeye-dev/matchmind/blob/3be1f22d66b880cc9501a15f31101b445f947c4b/matchmind/orchestrator.py))

MatchMind’s “Vision” consumes **10 Hz synthetic ball positions and known possession identities**, with official events passed through. It reconstructs passes, shots, tackles, interceptions, saves and goals; it does not perform video object detection or track all 22 players. Its shot classifier’s checked-in validation results concern data from its own simulator family, not real footage. Video metadata, description and author chapter markers were verified during this review, but captions failed and **frames/audio were not watched**. The conclusions therefore rest on inspected source and metadata, not an independently observed video demonstration. ([Tracking contract](https://github.com/auroraeye-dev/matchmind/blob/3be1f22d66b880cc9501a15f31101b445f947c4b/matchmind/sim/tracking.py), [Vision implementation](https://github.com/auroraeye-dev/matchmind/blob/3be1f22d66b880cc9501a15f31101b445f947c4b/matchmind/agents/vision.py), [Research verification record](../research_notes/Foundry%20Analyst%20Mode%20design/matchmind.md))

Adopt Crew’s bounded queue, deadlines, recent-insight memory and concise output contracts. Improve on both projects’ numeric grounding checks: a number appearing somewhere in the packet does not prove it belongs to the claimed player, time window or causal explanation. Footie should validate evidence identity, units, scope and revision, and allow specialists to return insufficient evidence. Implement independently: MatchMind has an MIT license; Crew declares MIT in package metadata but its inspected tree lacks a separate license file. ([Crew scheduling and guards](https://github.com/timsheldon1/matchday-crew/blob/374de95f4f7474c9a784e01a3ceafb2ce0a16ad5/src/agents/crew.js), [MatchMind grounding](https://github.com/auroraeye-dev/matchmind/blob/3be1f22d66b880cc9501a15f31101b445f947c4b/matchmind/llm/guardrails.py), [MatchMind license](https://github.com/auroraeye-dev/matchmind/blob/3be1f22d66b880cc9501a15f31101b445f947c4b/LICENSE), [Crew package](https://github.com/timsheldon1/matchday-crew/blob/374de95f4f7474c9a784e01a3ceafb2ce0a16ad5/package.json))

## Cover every metric without inventing measurements

Footie already has canonical event identities, revisions, occurrence and availability times, related actors, coordinates and optional authored xG, completion probabilities and flight times. It does **not** have measured continuous player tracking; its pitch animation reconstructs movement. Missing measurements must remain unavailable rather than silently become zero. Derived indices need named definitions and provenance in their evidence panels. The table below is the reference coverage contract, not a statement that every field is already implemented. ([Current Action contract](../backend/counterpress/personalization/contracts.py), [Current reducers](../backend/counterpress/personalization/metrics.py), [Existing-system audit](../research_notes/Foundry%20Analyst%20Mode%20design/existing.md))

| Metric family | Reference outputs to cover | Footie implementation rule |
|---|---|---|
| Match state | Clock, period, score, possession team | Resolve only events and revisions available at the playback boundary; exclude final-result metadata from earlier windows. |
| Team actions | Goals, shots, on target, passes/completions, final-third entries, tackles won, interceptions, pressures, fouls, cards, corners | Count explicit classified events. Preserve unknown outcomes and incomplete category coverage. Distinguish red/yellow cards. |
| Passing | Length, forward progression, completion rate, total completed distance, hardest completed pass, average difficulty | Geometry in metres; rate with known-outcome denominator and coverage. Difficulty is an estimate, not a measured quality score. Prefer existing calibrated completion probabilities where supported. |
| Shooting | Distance, xG, cumulative xG, shot/ball speed, outcome/body part, shot map | Keep supplied/modelled xG versioned. Compute speed only with valid authored flight duration or real telemetry; never infer flight time from gaps between events. |
| Possession and pressing | Possession seconds/percentage, rolling five-minute possession, PPDA | Event-interval possession is an estimate. MatchMind’s PPDA is all opponent passes divided by tackles won, interceptions and fouls, so expose that only as a named proxy or implement a separately defined zone-restricted measure. |
| Match dynamics | Momentum, chaos, tempo/rhythm and change from baseline | Explicit derived indices. Count distinct events for tempo; the reference rhythm counter can count several internal contributions per event. Do not portray these indices as empirically calibrated probabilities. |
| Player contribution | Recorded involvement/touches, passes/completions/accuracy, shots, goals, assists, xG, tackles, pressures | “Touches” in MatchMind means event involvement. Use truthful labels; assists require linked evidence. Include denominator, appearance interval and role context. |
| Movement | Carry progression/distance, top speed, sprint count, accumulated distance, hardest shot | MatchMind distance is elapsed minutes multiplied by a role/stamina rate; its sprints count qualifying event rows. Genuine movement metrics require a continuous synthetic or measured trajectory stream with documented sampling and sprint segmentation. |
| Spatial views | Team/player heatmaps, shot map, pass routes | Current event coordinates support on-ball activity maps. Off-ball occupancy, compactness and line height require full-player tracking. |
| Rankings and milestones | Top players, passing milestones, distance thresholds, speed/shot alerts | Document rating formula and role bias; prefer evidence-led player impact over an unexplained universal rating. Trigger only on supported quantities. |
| Audience presentation | Favorite player/club, language, analyst/casual depth, relevance, confidence, timed overlays, player labels and anchors | Personalize emphasis and vocabulary while retaining identical source facts. Confidence is qualitative evidence strength, not an uncalibrated percentage. |
| Operations and detection | Per-agent latency/status, calls/errors/allowance; truth/detected/matched events, precision/recall and score/pass parity | Track real runtime receipts. Auto-eventing accuracy requires a separate labelled telemetry test; it cannot be claimed from the current event reader. |

This inventory follows the pinned MatchMind interpreter, renderer and player views. Its xG uses hand-authored logistic coefficients; pass difficulty combines length, pressure and progression. Its player distance and sprint estimates are particularly unsuitable to copy as verified movement. ([Interpreter](https://github.com/auroraeye-dev/matchmind/blob/3be1f22d66b880cc9501a15f31101b445f947c4b/matchmind/agents/interpreter.py), [Simulator](https://github.com/auroraeye-dev/matchmind/blob/3be1f22d66b880cc9501a15f31101b445f947c4b/matchmind/sim/engine.py), [Player views](https://github.com/auroraeye-dev/matchmind/blob/3be1f22d66b880cc9501a15f31101b445f947c4b/web/extras.js), [Renderer](https://github.com/auroraeye-dev/matchmind/blob/3be1f22d66b880cc9501a15f31101b445f947c4b/matchmind/agents/renderer.py))

The complete MatchMind moment set is **pass combination, great pass, big chance, goal, pressure spike, card, substitution, halftime, fulltime, momentum swing, tempo shift, chaos phase, control phase, stat check and milestone**. Footie should support these trigger families with warmups, cooldowns and source requirements, rather than copy arbitrary thresholds as established football science. Crew additionally provides box entries, high recoveries, key/progressive passes, saves, red cards and goal-state narratives such as equalizers or taking the lead. These are useful extensions where the canonical evidence supports them. ([MatchMind triggers](https://github.com/auroraeye-dev/matchmind/blob/3be1f22d66b880cc9501a15f31101b445f947c4b/matchmind/agents/interpreter.py#L237), [Crew analyst](https://github.com/timsheldon1/matchday-crew/blob/374de95f4f7474c9a784e01a3ceafb2ce0a16ad5/src/analyst.js))

## Put bounded orchestration inside Foundry

Use a **Foundry-hosted Analyst Director** to run explicit, bounded orchestration over four separately versioned native prompt agents: **Chances**, **Build-up**, **Transitions**, and **Player impact**. Deterministic code supplies the statistics; specialists test interpretations and competing explanations. The director selects the strongest consequence, retains a counterpoint where justified, and proposes an observable next development. Each finding should contain its packet ID, cutoff, evidence and metric IDs, explanation, alternative interpretation, watch-next condition and expiry. Avoid persistent conversations that can carry later-match knowledge into a rewind.

This is preferable to starting a new visual workflow: Microsoft’s current documentation says that feature retires on **1 December 2026**, with Agent Framework/hosted deployment the migration path. Native prompt-agent A2A is a cheaper hosting alternative, but the research did not establish hard forwarding of specialist token caps or complete nested accounting. A hosted director can explicitly limit calls, concurrency, output tokens and retries. Current hosted deployment supports East US and creates a dedicated agent identity; existing Container App model permissions do not automatically authorize native project execution. ([Workflow migration](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/workflow), [Hosted deployment](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/deploy-hosted-agent), [Native A2A](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/enable-agent-to-agent-endpoint), [Detailed API blueprint](../research_notes/Foundry%20Analyst%20Mode%20design/foundry.md))

The proposed path is **canonical store → Container App snapshot/admission gateway → Foundry-hosted director → native specialists → validated finding → Analyst Mode**. Every packet pins occurrence cutoff, revision availability, delivery ceiling, source digest and agent versions. Seeking, changing match or receiving a correction invalidates the generation immediately; a delayed result cannot publish merely because its model call completed. Cache shared analysis by canonical packet and agent manifest, with audience presentation isolated appropriately. Continuously update cheap metrics, but dispatch agents only at meaningful state changes or bounded window intervals. Stop dispatch while paused or hidden, coalesce revisions, and show a time-labelled insight without freezing playback.

The **US$200 total budget** requires an application ledger, not just Azure alerts. The read-only audit reports about **US$5.97** subscription month-to-date spend, with billing lag and trial-credit expiry unverified; the existing alert budget remains US$125 until deliberately updated. Public East US hosted list rates are **US$0.0994/vCPU-hour plus US$0.0118/GiB-hour**: one vCPU and two GiB is about **US$0.123/hour**, but continuous operation would cost about US$88.56 over 720 hours. Configure two-minute idle timeout, one shared match session, explicit stop/cleanup, per-session duration limits and lifetime reservations. A proposed four-call window at 10,500 input/2,200 output mini tokens is about **US$0.00772** at public global rates; this is a planning estimate, not measured usage. Reserve worst-case spend atomically before dispatch, retain reservations for unknown failures, and fail closed to metrics/cached output if admission storage is unavailable. ([Account audit](../research_notes/Foundry%20Analyst%20Mode%20design/existing.md), [East US hosted prices](https://prices.azure.com/api/retail/prices?$filter=productName%20eq%20%27Foundry%20Agents%27%20and%20armRegionName%20eq%20%27eastus%27), [Model rates](https://prices.azure.com/api/retail/prices?$filter=contains%28meterName%2C%20%274.1%20mini%27%29%20and%20armRegionName%20eq%20%27eastus2%27), [Hosted lifecycle](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/manage-hosted-agent))

## Make the match central and prove usefulness

Add a lazy-loaded **Analyst Mode** route reached from Matchday’s **Watch full match** entry. Preserve Footie chat, Clubhouse and Match Centre. The first supported full-match library should match the existing three GI fixtures; the fourth career showcase needs its own replay parity work before inclusion. Expose a replay clock callback so the analytical packet boundary follows the completed action, not a separate timer. On desktop, place the pitch beside one editorial lead and a compact specialist strip; keep metric lenses and evidence expandable below. On mobile, order the experience as replay, current finding, then specialist/metric detail. Avoid six competing chat feeds, edge-aligned controls or large empty panels. ([Router](../frontend/src/App.tsx), [Matchday](../frontend/src/matchday/Matchday.tsx), [Replay component](../frontend/src/gi/PlaySequence.tsx), [Library](../frontend/src/gi/catalog.ts))

The release criterion should include **insight usefulness**, beyond schema validity. Test unseen windows for a supported pattern, a meaningful match consequence, and a sensible next observation; reject bland event repetition and unsupported tactical certainty. Independently verify deterministic metrics, missing coverage, unknown outcomes, two-half boundaries, revisions/retractions, rewind, stale async results, duplicated deliveries, partial agent failure, malformed output, admission races and retry accounting. Compare the native system with the existing observation layer on the same pinned windows. Browser checks must cover desktop/mobile, keyboard navigation, pause, seek, speed changes and an extended replay. A paid native smoke must confirm actual agent definitions, pinned versions, execution and traces; a local mock or external-agent registration cannot establish native deployment. Existing protected-main CI and exact-commit deployment gates remain the release path. ([Current integration and validation seams](../research_notes/Foundry%20Analyst%20Mode%20design/existing.md), [Deployment workflow](../.github/workflows/deploy.yml))

## Conclusion

The distinctive opportunity is a system that can say **what changed, why it could matter, what evidence challenges that reading, and what would confirm it next**. Specialist count is secondary to that contract. Honest coverage and causal snapshots also create a practical upgrade path: real tracking or video perception can later replace authored telemetry without rewriting the reasoning or interface. The immediate engineering priority is to prove this bounded native execution path on a small set of match windows, then expand coverage only where the data and measured results justify it.
